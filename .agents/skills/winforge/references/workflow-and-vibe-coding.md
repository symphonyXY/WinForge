# 需求引导与 Vibe Coding 协作规范

本手册定义 AI 与“无开发基础、靠 Vibe Coding 实现想法”的用户协作时的沟通方式与推进节奏。目标：**让用户轻松听懂、少走弯路、快速看到真东西、改起来不心累。**

---

## 1. 大白话沟通原则

- **翻译掉技术黑话**：不要直接抛“IPC 信道、预加载隔离、虚拟 DOM、水合、自包含运行时、NSIS 脚本”等词。必须提到时，用生活化比喻一笔带过（例如把自包含打包说成“把运行环境一起塞进安装包，新电脑不用额外下东西”）。
- **给选择，不丢空白题**：提问时不要只问“你想要什么架构/什么风格？”，必须给出 **2–3 个清晰选项 + 1 个明确推荐项 + 一句话理由**，让用户拍板即可。
- **拒绝过度盘问**：一轮最多问 **2–4 个最影响方向的决定**；能靠常识合理默认的小细节（比如快捷键、常规间距、错误提示文案）直接先做好，做完让用户看效果再微调。
- **坦诚说清边界**：如果某个需求在 Windows 上有限制（比如修改系统敏感设置需要管理员弹窗、或者某些第三方网站有防爬限制），提前用平实语言说明并给出替代思路，绝不敷衍或隐瞒。

---

## 2. 接到模糊需求时的“4 问定调法”

当用户只说了一个大概想法（例如：“我想做一个桌面番茄钟”“帮我写个本地图片压缩工具”），按以下维度挑出**真正还没定**的 2–4 个问题来问（用户已经说过的绝不重复问）：

1. **核心玩法（只盯最常用的那一件事）**
   - 问法示例：“这个工具你平时最常用的一步流程是什么？比如是‘拖图片进来 → 一键压缩 → 自动存到原文件夹旁边’，还是需要提前挑质量/尺寸？”
2. **视觉风格拍板（二选一或混搭）**
   - 选项 A（Apple OS 27 全生态液态玻璃风）：通边液态侧栏 + 统一工具条、无级透度玻璃（极透到染色高实底）、克制精致、灵动岛反馈；如需迷你挂件或控制面板，自然融合 Smart Stack 与三分区控制中心。
   - 选项 B（OriginOS 7 空间光影原子风）：柔和自然弥散光影、三档动态材质（拟真/自然/柔和）、Dynamic Glow 随手光晕、原子卡片原位放大、Origin Workbench 多任务工作台与 Q 弹流体手感（轻松/陪伴类工具还可按需开启 Glint/Wiggle 轻趣味风味）。
   - 选项 C（按部位混搭）：例如“整体用 Apple 通边玻璃骨架，状态提示用 OriginOS 原子岛 + 多任务工作台”。
3. **外观、窗口形态与智能能力**
   - 默认推荐：**浅色/深色自动跟随系统**（OriginOS 风格可附带夜间护眼 4.0）+ 一体化无割裂顶栏（保留右上角精修圆润窗口按钮）。如果软件适合常驻桌面角落（悬浮小组件/托盘工具），主动提一句可选 watchOS 风格 Smart Stack 迷你窗。
   - 只有当用户明确要做 AI 助手、文档摘要、截屏识别或智能建议功能时，再按需读取 [AI 与情景交互范式](ai-and-contextual-patterns.md) 对齐对应交互。
4. **技术架构推荐（由 AI 主动提案，用户拍板）**
   - 按 [架构选型与离线打包铁律](architecture-and-packaging.md) 给出 1–2 个大白话推荐（例如：“这个工具注重高颜值玻璃动效，我建议用 **Electron**，好处是新电脑 100% 装完即用零踩坑、动效还原最稳；如果你更在意安装包要很小且主要在 Win11 用，也可以选 **Tauri**。你倾向哪个？”）。

## 3. “先出最小雏形，再边看边精修”的推进节奏

确认方向后，不要闷头一次性写完几十个功能导致出错难查，按三步推进：

### 第一步：立住高颜值可运行雏形（MVP）
- 搭好规范干净的项目目录（见 [文件夹管理与开发规范](project-hygiene-and-standards.md)）。
- 打通**1 条最核心的真实功能链路**（从打开软件 → 操作主功能 → 看到真实结果 → 保存/关闭）。
- **第一版就必须颜值在线**：不要先交一个丑陋的线框白页再说“后面再美化”。雏形就要带有一体化融合顶栏、选定的 Apple/OriginOS 玻璃光影质感、精修按钮与流畅弹簧动效。
- 完成后告诉用户：**怎么双击/运行看效果**，并邀请用户亲手点一遍提意见。

### 第二步：逐轮打磨细节与扩展功能
- 每次只围绕用户指出的 1–3 个修改点集中优化，避免乱动没让改的地方。
- 涉及视觉微调（圆角大小、毛玻璃通透度、按钮按压弹性、颜色深浅）时，统一修改样式变量文件，保持全软件风格一致。
- 每完成一个用户满意的大版本，主动提醒做一次 Git 存档。

### 第三步：离线打包与人话交付
- 按 [架构选型与离线打包铁律](architecture-and-packaging.md) 打包出离线一键安装版 `Setup.exe`（放入 `release/` 文件夹）。
- 交付清单用通俗中文写清：
  1. **本次完成了什么 / 改了哪里**（3–5 条简明要点）；
  2. **软件在哪里打开 / 安装包在哪个路径**；
  3. **已验证过哪些场景**（诚实区分“我已实测通过”和“需要你在电脑上点开确认”）；
  4. **如果发现问题或想继续优化，下一步怎么提最方便**。

---

## 4. 出错时的排查沟通规矩

- 软件报错或打包失败时，**不要把几百行英文报错直接糊用户脸上**。
- 先自己定位根因并尝试修复；如果确实需要用户配合（例如杀毒软件拦截、某个文件被占用、需要确认权限），用 2–3 句大白话说明“出了什么情况 + 为什么 + 你只需做哪一步”。
- 严禁靠删掉功能、注释掉检查或降低画质来掩盖 Bug。
